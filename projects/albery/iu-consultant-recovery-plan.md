## Как продолжать работу в новом диалоге

Любой агент, получивший задачу про «ИИ-менеджера», «консультанта ИУ», Telegram-воронку или
«агент тупит», обязан:

1. Прочитать этот файл полностью.
2. Найти раздел [Текущее следующее действие](#текущее-следующее-действие).
3. Проверить, что снимок репозитория и production не изменился после последней записи в журнале.
4. Если задача свободна, сменить её статус с `NEXT` на `IN_PROGRESS` и добавить строку в
   [Журнал реализации](#журнал-реализации).
5. Работать только над этой атомарной задачей. Соседние дефекты записывать в backlog, а не
   смешивать в один коммит.
6. Сначала закрепить реальный провал воспроизводящим тестом, затем исправлять код.
7. Прогнать полный deploy-gate Albery вне production, развернуть по регламенту и проверить
   результат на реальной системе.
8. Только после evidence сменить статус на `DONE`, записать коммит, тесты, production-проверку
   и назначить ровно одну следующую задачу со статусом `NEXT`.
9. Зафиксировать изменение работающей Albery отдельной закрытой задачей Bitrix по
   [change-tracking.md](change-tracking.md).
10. Обновить этот файл, section index, changelog Hermes Brain, выполнить валидацию и синхронизацию.

Если production расходится с этим документом, нельзя молча «исправить историю». Нужно записать
новый факт в evidence log, отметить затронутую задачу `BLOCKED` или `IN_PROGRESS` и только затем
обновить маршрут.

## Словарь статусов

| Статус | Значение |
|---|---|
| `DONE` | Реализовано, тесты зелёные, production проверен; evidence записано |
| `IN_PROGRESS` | Один агент сейчас выполняет задачу |
| `NEXT` | Ровно одна следующая разрешённая задача |
| `NOT_STARTED` | Ещё не начинали или нет подтверждённой реализации |
| `BLOCKED` | Нужен факт, решение владельца или внешнее изменение; причина записана |
| `SUPERSEDED` | Решение заменено более новым; история и ссылка на замену сохранены |
| `LEGACY_LIVE` | Старый механизм работает в production, но не соответствует целевой архитектуре |
| `PARTIAL` | Есть часть механики, но критерии приёмки ещё не выполнены |

Правила статусов:

- `DONE` без commit hash, теста и production evidence запрещён.
- «Код написан» и «тесты зелёные» не означают `DONE` без проверки production.
- Ошибку нельзя закрыть новым текстом промпта, если причина лежит в состоянии, инструментах,
  маршрутизации или базе знаний.
- Одновременно допускается максимум один `IN_PROGRESS` и ровно один `NEXT`, если нет блокера.
- Нельзя расширять автономию агента, пока не пройдены ворота фазы `P4`.

## Целевой продукт

На ближайшем этапе система — **ИИ-консультант первой линии и помощник живого менеджера**, а не
полностью автономный продавец.

Хороший консультант:

- сначала отвечает на реальный вопрос клиента;
- учитывает уже сообщённые факты и не спрашивает их повторно;
- задаёт максимум один полезный следующий вопрос;
- не проталкивает анкету по факту первого сообщения;
- не выдумывает условия, цифры, сроки, юридические и налоговые трактовки;
- не обещает действие до его подтверждённого выполнения;
- мягко адаптирует тон и длину ответа;
- при неопределённости не пропадает, а запускает отслеживаемую передачу человеку;
- меняет CRM только через проверенные серверные правила;
- оставляет полный машинно-читаемый след решения.

Не является целью текущей программы:

- имитировать человека или скрывать, что отвечает ИИ;
- любой ценой доводить каждого до анкеты;
- самостоятельно торговаться, давать скидки или трактовать договор;
- сохранять универсальный набор возможностей Hermes у клиентской модели;
- автоматизировать всю воронку до прохождения измеримых quality gates.

## Неподвижные продуктовые инварианты

1. **Ответ сначала.** Анкета, CTA или следующий этап идут после ответа на заданный вопрос.
2. **Один полезный шаг.** В одном ходе максимум один вопрос или один CTA.
3. **Не спрашивать известное.** Подтверждённые данные повторно не запрашиваются.
4. **Только утверждённые факты.** Коммерческие, числовые, налоговые и юридические ответы имеют
   версионированный источник либо уходят человеку.
5. **Никогда не молчать из-за сбоя.** Клиент получает короткое честное подтверждение; передача
   человеку имеет владельца, статус и SLA.
6. **LLM предлагает — код разрешает.** Модель не выполняет CRM- и документные мутации напрямую.
7. **Минимум полномочий.** У клиентского агента нет web, удаления, администрирования и общих
   внутренних инструментов.
8. **Стадия не является скриптом.** CRM-стадия — факт процесса; готовность, вопрос и возражение
   определяют содержание ответа.
9. **Действие, потом отчёт.** Нельзя сообщить «отправил», «перевёл», «создал» без postcondition.
10. **Наблюдаемость без PII-дублирования.** В trace хранятся версии, решения, источники, действия
    и исходы; полный клиентский текст не размножается по служебным таблицам.

## Целевая архитектура

```text
Telegram update
    ↓
Durable inbox + debounce + per-dialog ordering
    ↓
Context builder
    ├── CRM snapshot with version
    ├── structured conversation state
    ├── short recent history / rolling summary
    └── approved knowledge sources
    ↓
LLM → strict TurnPlan
    ↓
Policy validator
    ├── allowed action?
    ├── facts and sources valid?
    ├── state transition valid?
    └── handoff required?
    ↓
Transactional executor
    ├── Telegram outbox
    ├── CRM mutation with idempotency + postcondition
    └── tracked human handoff
    ↓
Atomic state update + full decision trace + quality metrics
```

Минимальный контракт `TurnPlan`:

```json
{
  "reply": "Текст для клиента",
  "intent": ["conditions"],
  "answered_questions": ["commission"],
  "unresolved_questions": [],
  "next_action": "reply_only",
  "state_patch": {},
  "confidence": 0.91,
  "source_ids": ["iu-commercial-facts-v1"],
  "handoff_reason": null
}
```

Это пример структуры, а не готовая схема. Финальная схема должна запрещать неизвестные поля,
валидировать enum и не позволять модели передавать произвольные tool names или аргументы мутаций.

## План реализации

### P0 — безопасность и прекращение отпугивающего поведения

Цель фазы: сделать текущую live-систему безопасной и предсказуемой до архитектурной перестройки.

| ID | Задача | Статус | Зависимости |
|---|---|---|---|
| `IU-P0-00` | Аудит, канонический план и исходный evidence | `DONE` | — |
| `IU-P0-01` | Минимальный безопасный набор возможностей клиентского агента | `DONE` | `IU-P0-00` |
| `IU-P0-02` | Убрать принудительную анкету; ответ-first и один CTA | `DONE` | `IU-P0-01` |
| `IU-P0-03` | Гарантировать клиентский ответ при сбое и управляемую передачу человеку | `IN_PROGRESS` | `IU-P0-01` |
| `IU-P0-04` | Типизировать отображение полей и вынести важную математику из LLM | `NEXT` | `IU-P0-01` |
| `IU-P0-05` | Закрепить P0 реальными replay/E2E-регрессиями | `NOT_STARTED` | `IU-P0-02..04` |

Критерии выхода из P0:

- у клиентского runtime нет web, delete/admin/report/code tools;
- server-side policy отклоняет неразрешённое действие, даже если модель его запросила;
- приветствие или off-topic не вызывает автоматическую отправку анкеты;
- на заданный вопрос сначала приходит ответ либо явный handoff;
- модельный сбой не создаёт тишину;
- идентификатор никогда не форматируется как деньги;
- все найденные в аудите P0-провалы воспроизводятся тестами и проходят после исправления;
- полный predeploy gate зелёный, production проверен без сообщения реальному клиенту «ради теста».

### P1 — правда, естественный разговор и строгий контракт хода

### Ключевые проектные решения

- **Порог уверенности собирается из трёх слагаемых**, а не из само-оценки модели: поиск `0.45`,
  механическая опора на источник `0.35`, мнение модели `0.20`. Два из трёх проверяемы.
- **Число без источника — вето, а не штраф.** Средневзвешенный скор позволял высокому поиску и
  бодрой само-оценке перевесить проваленную проверку цифр: «для вас сделаем 20%» при источнике
  с 44% набирало `0.81` и ушло бы клиенту.
- **Строгий порог `0.95` — только для расчётов**, не для любого упоминания денег. Если считать
  расчётом каждое «%», порог требует поиска не ниже `0.89` даже при идеальной опоре, и самый
  частый вопрос воронки («сколько вы берёте») всегда уходил бы человеку.
- **Условия карточки «Человек: …» условные.** Принуждается кодом только безусловное
  («Человек: всегда»); «если клиент спорит с расчётом» уходит в промпт, решает модель.
- **Retrieval отсекается порогом ПОСЛЕ семантики**, иначе эмбеддинги могли бы лишь переставлять
  найденное лексикой, а не находить пропущенное.

### Разбор тестов старого протокола (`IU-R-07`)

57 тестов клиентской ветки были написаны против снятого протокола маркеров: починить их нельзя,
только переписать или удалить. Разобраны по одному, не файлами. **Ворота зелёные:**
`predeploy_check` — 1140 passed, 4 skipped.

Три дыры, которые нашёл именно этот разбор (и которые доказали, что удалять тесты вслепую было
нельзя):

1. **Повторная отправка.** Воронка убирала `send_terms`/`send_form` после доставки, поэтому на
   «условия не пришли, продублируйте» клиент не получал ничего: защита от дублей стала отказом
   выслать документ, который до него не дошёл. Введён `resend_requested` — единственная
   текстовая проверка, оставшаяся в слое воронки, и здесь она необходима.
2. **Карточка людям всегда говорила «клиенту отвечено»**: признак считался по непустому тексту,
   а текст эскалации непустой всегда. Введено `Outcome.answered_client`.
3. **Слово «оборот» включало режим расчётов**: вопрос агента «какой у вас оборот?» уводил ход
   под порог `0.95`. Существительные оборот/доход/выплаты убраны из словаря расчётов.

Осознанно изменённое поведение (решение, а не регрессия):

- при эскалации клиент получает короткую честную строку, а не тишину — инвариант «никогда не
  пропадать» важнее прежнего правила о молчании (22.07.2026);
- сделка заводится ПОСЛЕ хода и по факту разговора о продукте, а не по regex до него;
- «Связались» убран из цепочки, поэтому перехода на него больше нет.

Сверка анкеты НЕ потеряна: она живёт в фоновом стороже `_check_new_forms`, независимом от
клиентского хода; её 12 тестов целы.

### Блокеры выкатки

1. **База знаний ИУ пуста.** Документ «Что отвечать лидам» — шаблон `[ЗАПОЛНИТЬ]`. Конвейер
   готов, но при пустой базе агент честно эскалирует каждый вопрос. Заполняет владелец сам
   (решение 2026-07-26). Формат: `### Заголовок` + `Ответ:` обязательны; `Проще:`, `Этап:`,
   `Человек:` — по желанию. Ручные списки формулировок НЕ нужны — за это отвечает семантика.
2. **Коды этапов «Подписание договора» и «Договор подписан» неизвестны.** В `iu_funnel.py`
   стоят заготовки `CRM_STAGE_SIGNING`/`CRM_STAGE_SIGNED`. Нужны реальные `STATUS_ID` из
   портала. С машины владельца доступа к Битриксу нет (нет `.env` с ключами портала и
   deploy-хелпера) — достаёт владелец или агент с сервера.
3. **Сделки на убираемом «Связались» надо перенести** на «Новый клиент» до удаления стадии.
   Пока стадия жива, код читает её как «Новый клиент» и ничего не теряет.
4. **`contract_signed` не имеет источника правды.** Поля «договор подписан» в воронке нет,
   поэтому на этап «Договор подписан» сделку переводит человек. Придумывать признак нельзя.

- Не удаляет `iu_turn_policy.py`: он вплетён в `funnel_rules`, а тот — в кабинет (`funnel_view`)
  и MCP. Снос требует отдельного атомарного изменения; делать его в одном релизе с переключением
  рантайма без shadow-режима безрассудно.
- Не даёт UI для списка запрещённых фраз: колонка `blocked_phrases` и чтение готовы,
  текстовое поле в кабинете — нет.

## Decision log

Решения append-only. Если решение меняется, добавляется новая запись с `supersedes`, старая не удаляется.

### `D-001` — один канонический план

- **Дата:** 2026-07-25
- **Решение:** текущий статус восстановления живёт только в этом файле.
- **Причина:** прошлые планы, changelog и `iu-funnel.md` смешивали справочник, историю и roadmap.
- **Следствие:** любой агент начинает с `Current next action`; другие документы ссылаются сюда.

### `D-002` — консультант первой линии до прохождения quality gates

- **Дата:** 2026-07-25
- **Решение:** не считать систему автономным продавцом до завершения P4.
- **Причина:** реальными переписками подтверждены давление, ошибки расчёта, молчание и потеря handoff.
- **Следствие:** важные, рискованные и неоднозначные случаи передаются человеку.

### `D-003` — LLM предлагает, код разрешает и исполняет

- **Дата:** 2026-07-25
- **Решение:** модель формирует строгий `TurnPlan`, но не получает произвольную мутацию.
- **Причина:** prompt не является границей безопасности или гарантом бизнес-инвариантов.
- **Следствие:** policy, idempotency, postconditions и state transitions реализуются серверно.

### `D-004` — стадия CRM не диктует реплику

- **Дата:** 2026-07-25
- **Решение:** стадия остаётся фактом процесса; ответ определяется вопросом, intent, readiness и фактами.
- **Причина:** текущая stage-first логика создаёт ощущение скрипта и игнорирует multi-intent.
- **Следствие:** этапы не обязаны проходиться как последовательность обязательных сообщений.

### `D-005` — никакой тишины при handoff или сбое

- **Дата:** 2026-07-25
- **Решение:** клиенту всегда подтверждается, что вопрос принят; внутреннее обещание отслеживается.
- **Причина:** fire-and-forget карточки уже приводили к часам ожидания и потерянным ответам.
- **Следствие:** handoff — отдельная сущность с owner/status/SLA, а не запись в группе.

### `D-006` — тестировать outcomes, а не наличие текста сценария

- **Дата:** 2026-07-25
- **Решение:** gold/replay/E2E должны проверять ответ, действия, state и CRM postconditions.
- **Причина:** строковые тесты проходили при плохом клиентском результате.
- **Следствие:** любое найденное клиентом поведение становится регрессией полного turn.

### `D-007` — emergency P0 начинается с нулевой поверхности инструментов

- **Дата:** 2026-07-25
- **Решение:** до появления server-side knowledge prefetch и типизированных actions customer
  connector работает с `tools=[]`; нужные возможности возвращаются по одной после отдельных gates.
- **Причина:** исходные 119 tools несоразмерны консультации, а у Hermes v0.17 нет совместимого
  per-invocation лимита для используемого top-level `-z`.
- **Следствие:** обычный текстовый ответ остаётся возможен, tool-loop структурно невозможен;
  knowledge/handoff добавляются только через ограниченный controller, не возвратом общего MCP.

## Риски и стоп-условия

| Риск | Уровень | Стоп-условие / реакция |
|---|---|---|
| Разрушающее действие из клиентского prompt | Critical | Остановить расширение поведения; закрыть allowlist и policy |
| Неверное коммерческое/юридическое утверждение | Critical | Откатить релиз или отключить affected intent; передать людям |
| Клиент остаётся без ответа | Critical | Включить fallback/handoff; расследовать delivery и owner SLA |
| Массовое повторение анкеты/документа | High | Kill switch соответствующего action; replay + fix |
| Состояние сделки расходится с CRM | High | Запретить дальнейшую мутацию до readback/reconciliation |
| `p95` полезного ответа выше 20 секунд | Medium/High | Уменьшить последовательные LLM/tool hops, включить fallback |
| Не хватает утверждённого бизнес-факта | Expected blocker | Не угадывать; добавить вопрос владельцу и временный handoff rule |
| Production нельзя проверить безопасно | Blocker | Не ставить `DONE`; записать точный blocker |
