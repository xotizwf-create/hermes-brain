# /албери — рабочий цикл по задачам Albery

Владелец ставит задачу в Битриксе на портале Albery и вешает тег **Claude**. По команде
`/албери` эта задача попадает ко мне: я её выполняю, пишу результат в саму задачу и
отчитываюсь в Telegram. Никаких пересказов «что бы я сделал» — цикл доводится до конца.

**Над очередью работает несколько агентов** (Claude Code, Hermes, codex, будущие). Поэтому
задача сначала ЗАХВАТЫВАЕТСЯ — отметкой в самой задаче, — и только потом делается. Чужую
занятую задачу не трогать ни при каких обстоятельствах: берём следующую свободную.

**Обязательный контекст перед работой:** `CLAUDE.md` в репозитории Albery
(`c:\Users\Администратор\Новая папка\Albery\CLAUDE.md`) — 11 правил безопасной работы с прод-системой.
Они действуют целиком, этот скилл их не смягчает. Инженерный журнал изменений —
`projects/albery/change-tracking.md`.

## Доступ

Скрипты скилла лежат в `scripts/` рядом с этим файлом. Всё идёт через один вход:

```bash
cd ".claude/skills/albery/scripts"
python albery_run.py exec   albery "<команда на 186>"
python albery_run.py script albery ./<файл.py> [аргументы]   # зальёт и выполнит
python albery_run.py put    albery ./<файл.txt>              # только зальёт
python albery_run.py exec|script|put main ...                # то же для 217 (Hermes Brain)
```

Маршрут: ПК → 217.198.12.236 (пароль из gitignored `Albery/.env`) → пароль Albery из сейфа
на 217 → 186.246.7.32. Пароль Albery не попадает на этот компьютер и не светится в `ps`.
Залитые файлы живут на цели в `/root/claude_tasks/`.

Две особенности среды на этом ПК (иначе команды падают):
- `PYTHONIOENCODING=utf-8` — иначе консоль cp1251 давится русским выводом;
- `MSYS_NO_PATHCONV=1` — иначе Git Bash превращает `/root/...` в `C:/Program Files/Git/root/...`.

**Кто я в очереди.** В начале работы задать себе идентификатор `Claude Code/<8 символов id
сессии>` (берётся из пути scratchpad'а) и подставлять его в `--agent` во ВСЕХ вызовах. Два
экземпляра одного инструмента — разные агенты, поэтому идентификатор обязан включать сессию.

## Цикл

### 1. Осмотреться (обязательно, до всего)

Со мной в этой же системе может параллельно работать другой агент, а прод-дерево само
коммитит и пушит:

```bash
python albery_run.py exec albery "cd /var/www/albery && git log --oneline -15 && git status --short && systemctl is-active albery && free -m"
```

Локальный клон Albery подтянуть к актуальному `origin/main` перед любой правкой кода.

### 2. Забрать очередь

```bash
python albery_run.py script albery ./list_claude_tasks.py --agent "Claude Code/<сессия>"
python albery_run.py script albery ./list_claude_tasks.py --agent "..." --all   # + закрытые
```

Отбор — по тегу, содержащему слово `claude` в **любом написании**: `Claude`, `#Claude`,
`claude-code`. Завершённые (5) и отклонённые (7) отсеиваются. По каждой задаче печатается
**СОСТОЯНИЕ**: `СВОБОДНА` / `ЗАНЯТА — держит <агент> с <время>` / `МОЯ`, её теги, а в конце —
список свободных номеров. Описание и лента комментариев читаются живьём из IM-чата задачи
(снимок в БД отстаёт).

Почему поиск устроен просмотром, а не фильтром портала: Битрикс ищет по тегу **только
точным совпадением** — `{'%TAG': 'Claude'}` ведёт себя как точное, список значений
`{'TAG': ['Claude', '#Claude']}` возвращает пусто, а метода перечисления тегов нет
(`tasks.tag.list` → 404). Поэтому открытые задачи листаются постранично, а теги сверяются
в коде. Ловушка стоила пропущенных задач 27.07.2026: три задачи владельца с тегом `#Claude`
были невидимы, потому что фильтр искал ровно `Claude`.

Если свободных задач нет — так и сказать владельцу, ничего не выдумывать и **ничего не
перехватывать**.

### 3. Взять задачу в работу (захват)

Работать можно только над захваченной задачей. Берём первую свободную по возрастанию номера:

```bash
python albery_run.py script albery ./claim_task.py <id> "<точное название>" --agent "Claude Code/<сессия>"
```

Коды возврата: **0** — задача моя, можно работать; **2** — занята другим агентом, берём
следующую свободную; **1** — ошибка, разбираться.

Что делает захват: пишет в задачу комментарий `🔒 ВЗЯЛ В РАБОТУ: <агент> · <время МСК>`,
переводит задачу в статус «выполняется» и через 6 секунд перечитывает ленту — если в тот же
момент захватил кто-то ещё, побеждает более ранний комментарий, а проигравший сам пишет
`🔓 ОСВОБОДИЛ ЗАДАЧУ` и уходит к следующей. Замок живёт в комментариях, потому что это
единственное место, которое одинаково видят все агенты и все люди.

Правила захвата — соблюдать буквально:

- **Есть чужая метка «взял в работу» без освобождения — задача НЕ моя.** Не писать в неё
  ничего, не менять статус, идти к следующей свободной. Это касается и меток в свободной
  форме от других агентов.
- **Замок старше 4 часов** помечается как подозрительный. Даже тогда **не перехватывать
  самому** — сообщить владельцу в Telegram и ждать его решения. Чужая незавершённая работа
  может быть в процессе деплоя.
- **Бросаю задачу — освобождаю явно.** Не доделал, упёрся в блокер, нужен ответ владельца
  и работа откладывается:
  ```bash
  python albery_run.py script albery ./claim_task.py <id> "<название>" --agent "..." --release "почему бросаю"
  ```
  Молча оставлять замок нельзя — задача повиснет для всей команды.
- **Уточняющий вопрос — не повод освобождать**, если продолжаю ждать ответ в этой же сессии:
  замок держим, в задачу пишем вопрос комментарием.

### 4. Разобрать задачу

Задачи берутся по одной, по возрастанию номера. Перед работой:
- прочитать описание и **критерий результата** — именно он определяет, что считается сделанным;
- прочитать комментарии: там бывают уточнения и скриншоты;
- определить, меняет ли задача работающую систему (код/конфиг/БД/промпты) или это разбор,
  анализ, отчёт — от этого зависит объём мер безопасности.

Если задача сформулирована так, что возможны разные толкования с разным результатом —
**не гадать**: написать в задачу уточняющий вопрос (`--comment-only`, задачу не закрывать)
и сообщить об этом владельцу в Telegram.

### 5. Выполнить с максимальной безопасностью

Правила из `Albery/CLAUDE.md`, коротко — но соблюдать по полному тексту:

1. **Бэкап до любого изменения.** Код — `tar` в `/var/backups/albery/code/` + точка отката в git;
   `.env`/конфиги — копия рядом; БД — `pg_dump` затрагиваемых таблиц. Нельзя сделать бэкап —
   не начинать изменение и честно об этом сказать.
2. **Конвейер:** правка локально → `pyflakes` → `pytest` (для Albery — `python scripts/predeploy_check.py`,
   красные ворота = деплоя нет) → push → на 186 `git pull --ff-only` → `py_compile` → рестарт →
   `scripts/deploy_smoke.py` → `journalctl -u albery -p err` чист.
3. **Рестарт — только в пустое окно** (`bitrix_inflight_turns` пуст, нет running-автоматизаций).
   Рестарт убивает живые ходы сотрудников. Без необходимости не рестартовать вообще.
4. **Бокс слабый (2 ГБ).** Перед тяжёлым — `free -m`. Сборка фронта и полные прогоны тестов —
   локально, на сервер уходит готовый `dist` атомарным свапом.
5. **Секреты** не попадают ни в git, ни в вывод команд, ни в задачу Битрикса.
6. **Разведка на тестовых объектах** (пометка «ТЕСТ — УДАЛИТЬ»), после — зачистка.
7. **Необратимое — только с явного «да» владельца**: удаления, массовые изменения, любая
   рассылка сообщений/задач живым людям. Сначала показать, что именно произойдёт.
8. **Тест до «готово»:** падающий тест, воспроизводящий жалобу → фикс → зелёные ворота →
   проверка на проде на тех самых реальных данных, о которых шла речь.

**Промпты и поведение агента не менять.** Правило владельца (27.07.2026): промпты, `SOUL.md`,
инструкции агента в БД (Маршрутная карта и пр.), тон и логика ответов — **не трогаются**.
Если задача их задевает даже краем — сначала описать владельцу, что именно придётся изменить
и почему, дождаться явного «да» и только потом делать. Молча «заодно подправить формулировку»
нельзя: у агента живые пользователи, и его поведение — согласованная вещь, а не деталь
реализации. Работаем аккуратно и узко: меняем только то, о чём задача, и ничего вокруг.

### 6. Проверить — коротко и по делу

Тесты не покрывают поведение агента: они гоняют функции на заготовленных входах, а человек
видит другое — от чьего имени пришёл ответ, что агент понял из живой формулировки, не
промолчал ли он при отказе. Поэтому «тесты зелёные» результатом не считается.

Но и гонять все сценарии подряд не надо — это часы работы на ровном месте. **Объём проверки
берётся по объёму правки:**

- правка не меняет поведение (доки, отчёт, разбор, чтение) — проверять нечего, так и пишем;
- точечная правка кода — прогнать ровно тот путь, который менялся, и посмотреть журнал:
  `journalctl -u albery -p err --since "-10 min"`;
- правка задевает то, что видит человек — **один сквозной прогон именно того случая, о котором
  была задача** (реальный диалог, реальное имя), и прочитать результат глазами человека:
  от кого пришло, как звучит, правильное ли время МСК.

Два правила, которые не отменяются никогда: **молчание — сломанная логика** (отказ обязан быть
сообщением, а не тишиной), и **что не проверено — так и написано** в задаче и в отчёте.
Выдавать непроверенное за проверенное нельзя: на эти слова будут опираться.

Тестовые объекты после прогона удалить.

### 7. Написать результат в задачу и закрыть

```bash
python albery_run.py put    albery <локальный result_<id>.txt>
python albery_run.py script albery ./finish_claude_task.py <id> "<точное название задачи>" \
    /root/claude_tasks/result_<id>.txt --agent "Claude Code/<сессия>"
# промежуточный комментарий/вопрос без закрытия (замок остаётся за мной):
python albery_run.py script albery ./finish_claude_task.py <id> "<название>" <файл> \
    --agent "Claude Code/<сессия>" --comment-only
```

Скрипт откажется писать, если задачу успел захватить другой агент, — это последняя страховка
от затирания чужой работы.

Как писать результат — **человеческим приятным техническим языком**:
- обращение по имени, спокойный деловой тон, без канцелярита и без жаргона ради жаргона;
- разделы BB-разметкой: `[b]Что сделано[/b]` → `[b]Проверка[/b]` (что и как проверено, с цифрами
  и цитатами вывода) → `[b]Что менялось в системе[/b]` (или «ничего, работа только на чтение») →
  при изменении кода `[b]Откат[/b]` (путь к бэкапу или `git revert <hash>`);
- если менялась работающая система — **обязательна ссылка на коммит**
  `https://github.com/xotizwf-create/Albery/commit/<hash>`, первопричина (root cause) и как проверено;
- не копировать формулировку владельца и не пересказывать чат — задача это инженерный документ;
- честно: что не сделано или не проверено — так и написать.

Закрытие задачи — сигнал «сделано» и одновременно снятие замка: закрытая задача больше не
попадает в очередь, и освобождение писать не нужно.

### 8. Инженерный журнал

Если по задаче менялась работающая система:
- одно атомарное изменение = один коммит в `github.com/xotizwf-create/Albery`;
- полный инженерный контекст (проблема, кто столкнулся, root cause, файлы, коммит, проверка,
  откат) пишется **в эту же задачу Claude** — она и есть закрытая задача журнала по правилу
  `projects/albery/change-tracking.md`, отдельную дублирующую заводить не нужно;
- строка в `logs/changelog.md` мозга — как обычно.

### 9. Мини-отчёт владельцу в Telegram

По **каждой** выполненной задаче — отдельное короткое сообщение в чат Hermes Brain:

```bash
python albery_run.py put    main <локальный report_<id>.txt>
python albery_run.py script main ./report_to_owner.py /root/claude_tasks/report_<id>.txt
```

Формат мини-отчёта (4–6 строк, без технических простыней):

```
✅ Задача #<id> «<название>» — выполнена
Что сделал: <1–2 предложения по сути>
Изменения в системе: <что затронуто и ссылка на коммит / «нет, работа на чтение»>
Задача: https://albery.bitrix24.ru/company/personal/user/<responsible>/tasks/task/view/<id>/
```

Если задача не доведена до конца (нужен ответ владельца, блокер, отказ по правилу
безопасности) — отчёт всё равно шлём, но честно: что сделано, где встали и что нужно.

## Грабли этого портала (проверено боем)

- **Комментарии НЕ удаляются и НЕ редактируются через REST** (`ACTION_NOT_ALLOWED`). Текст
  результата пишем начисто, один раз. Никаких «тестовых» комментариев в живой задаче.
- **Доказательство записи — только `comment_id`** из ответа инструмента. Читатели комментариев
  на этом портале отдают ложный ноль для только что созданного комментария. Нет `comment_id` —
  задача не закрыта, разбираться.
- **`expected_title` обязателен** в скриптах захвата и закрытия — защита от записи не в ту задачу.
- **Импорт `mcp.context_server` стартует живые планировщики Albery.** До импорта — `B24_TASK_OFFER=0`
  и `B24_TASK_CHECKIN=0` (в скриптах скилла уже сделано). Иначе фоновый скрипт начнёт писать
  живым сотрудникам.
- **Агент Албери (пользователь 24) сам отвечает в задачах** — его комментарий в ленте не мой
  результат и не захват. Мои записи идут от «ИИ Агент» (22), а кто именно из агентов —
  видно по идентификатору в метке замка.
- **Замок нельзя стереть** (комментарии неудаляемы) — только перекрыть комментарием об
  освобождении. Поэтому метка ставится осознанно, а не «на всякий случай».
- **Параллельный агент**: перед правкой перечитать файл/строку БД заново, `git pull --rebase`
  перед push, после деплоя смоук всего затронутого контура, а не только своего файла.
  Рестарт поднимает изменения обоих агентов разом — проверять и свою фичу, и соседние.
